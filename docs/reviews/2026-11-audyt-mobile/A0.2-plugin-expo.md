## 1. Podsumowanie i rekomendacja

**Rekomendacja: hybryda z przewagą pluginu.** Wszystkie skille, które upstream utrzymuje, bierzemy z oficjalnego pluginu
`expo@expo-plugins` i wołamy z przedrostkiem `expo:`. Lokalnie zostają tylko dwie rzeczy, których upstream nie ma:
1. nasz hub stosu, dziś pod kolidującą nazwą `expo-overview`. To w całości nasz tekst, a nie kopia upstreamu.
   Trzeba go przemianować.
2. `expo-tailwind-setup`, który upstream usunął.

Do tego nakładka dokłada blokadę wysyłki feedbacku i bramkę „plugin zainstalowany” w doctorze/bootstrapie.

Uzasadnienie:
1. **Kopia nie ma żadnej wartości dodanej poza opisami.** 15 z 17 skilli kopii różni się od `472d040` tylko trzema rzeczami:
   polskim `description`, wyciętą sekcją „Submitting Feedback” i pominiętymi katalogami `agents/` (metadane Codexa).
   Wyjątki to `expo-overview` (lokalny tekst, patrz §2.2) i `expo-module` (jedno dopisane zdanie). Wszystkie pliki
   `references/` są bajt w bajt identyczne z upstreamem.
2. **Kopia jest już merytorycznie nieaktualna, i to w kodzie, który buildery przepisują.** Przykłady:
   - `ThemeProvider theme=` zamiast `value=` (`expo-router`);
   - stringi `'cubic-bezier(...)'`, które Reanimated 4.1.1/4.5.1 odrzuca (`expo-animation`);
   - zalecenie usunięcia `expo-constants`, które psuje autolinking przy Expo Router (`expo-upgrade`);
   - SF Symbols przez `expo-image` zamiast `expo-symbols` (`expo-native-ui`);
   - `eas build --submit` zamiast `--auto-submit` (`eas-app-stores`).

   Szczegóły w tabeli w §2.3.
3. **Polskie opisy nie są potrzebne do wyzwalania.** Próba 8 promptów (4 PL + 4 EN) dała 8/8 trafień we właściwy skill
   pluginu z angielskimi opisami (§5). Buildery i tak nie polegają na wyzwalaniu: dostają skille przez `skills:`
   we frontmatterze.
4. **Pole `skills:` agenta przyjmuje `expo:expo-router`.** Potwierdziła to próba, log debug pokazuje
   `Preloaded skill 'expo:expo-router'` (§6). Wzorzec jest ten sam co `figma:figma-use` na webie.
5. **Plugin w Claude Code to dziś czyste skille plus jeden serwer MCP.** Nie ma hooków, agentów ani komend. Telemetria
   (hooki PostHog) została usunięta w `3d1ca4e`. Zostaje jedno realne ryzyko: instrukcja wysyłki feedbacku w każdym
   SKILL.md, bez warunku zgody użytkownika (§3). Zamyka ją reguła `deny` w nakładce.

Dlaczego nie czysty plugin: upstream nie ma skilla NativeWind, a nasz stack to NativeWind. Nie ma też naszych reguł stosu:
Supabase jako domyślny backend, Maestro, tabela RN-vs-web, na którą powołuje się hook `mobile-anti-pattern-check.sh`.
Dlaczego nie kopia: odświeżanie 17 kopii to stała praca, a kopia sprzed 10 tygodni już uczy builderów błędnego kodu.

## 3. Feedback i telemetria upstreamu

### 3.1. Stan dziś (HEAD `a9e5bd3`)

Każdy z 23 SKILL.md kończy się tą samą sekcją (przykład `expo-router`):

> ## Submitting Feedback
> If you encounter errors, misleading or outdated information in this skill, report it so Expo can improve:
> ```bash
> npx --yes @expo/agent-cli@latest feedback --category skills --subject "expo-router" "<actionable feedback>"
> ```
> Only submit when you have something specific and actionable to report. Include as much relevant context as possible.
> If an agent repeatedly fails at an Expo task or the user has to step in, submit a brief report of the task, expected
> result, and what went wrong using `--category evals` and the relevant Expo package or command as `--subject`.

`plugins/expo/README.md`: „Every skill includes instructions to submit specific, actionable feedback with
`npx --yes @expo/agent-cli@latest feedback`.”

**Ocena:**
- **Automatycznej telemetrii już nie ma.** Hooki i skrypty usunięto w `3d1ca4e`, więc samo użycie skilla niczego nie wysyła.
- **Instrukcja wysyłki jest skierowana do modelu i nie wymaga zgody użytkownika.** Wysyłka następuje z inicjatywy modelu
  („If you encounter errors…”, „If an agent repeatedly fails…”), a nie na prośbę użytkownika.
- Wysyłka uruchamia **niepinowany pakiet npm `@latest` z `--yes`**. Do Expo trafia treść uwagi, a w kategorii `evals`
  opis zadania.
- W 8 próbach z §5 i 2 próbach agentów **nie było ani jednego wywołania** `agent-cli`. Polecenie występuje w strumieniach
  wyłącznie jako treść wczytanego skilla.

  only the description. Subagents can still invoke unlisted project, user, and plugin skills through the Skill tool”;
- preładowanie obejmuje „up to the first 32 distinct names in the list”;
- brakujący skill: „If a listed skill is missing or disabled… Claude Code skips it and logs a warning to the debug log”.

**Dokumentacja nie mówi nic o nazwach z przedrostkiem pluginu.** Rozstrzygnęła to próba.

### 6.2. Próba `--agents`

Ustawienia: plik `a02/agents.json`, agenci-sondy z `tools: ["Read"]`. Każda sonda miała bez narzędzi zacytować nagłówek
i zdanie o `headerLargeTitleEnabled` z kontekstu.

Główna sesja widziała oba skille naraz (`expo-overview` i `expo:expo-overview` na liście `skills` w init), a log mówi
„0 duplicate/user-owned entries skipped”. Claude Code nie deduplikuje skilli lokalnych i pluginowych.

**Wnioski:**
- `skills: [expo:expo-router]` działa tak jak `figma:figma-use`.
- Nazwy w agentach należy pisać z przedrostkiem, żeby nie zależeć od tego, czy w projekcie leży stara kopia.
- **Brak pluginu w projekcie nie zatrzymuje buildera.** Preładowanie jest wtedy po cichu pomijane, ślad zostaje tylko
  jako WARN w logu debug.

## 8. Co trzeba zrobić w nakładce przy każdej opcji

### Opcja A: czysty plugin

1. `stacks/expo/settings.patch.json`:
   - `enabledPlugins: {"expo@expo-plugins": true}`;
   - `extraKnownMarketplaces: {"expo-plugins": {"source": {"source": "github", "repo": "expo/skills"}}}`;
   - reguły `permissions.deny` dla `agent-cli` (R1).
2. README nakładki, krok instalacji:
   `claude plugin marketplace add expo/skills` i `claude plugin install expo@expo-plugins --scope project`.
   Wzorzec to web README, kroki 2.
3. Usunąć z wariantu wszystkie katalogi `.claude/skills/{expo,eas}-*` (`usun.txt`).
4. Agenci: zamienić `skills:` na nazwy z przedrostkiem:
   - `feature-builder-mobile-ui`: `expo:expo-native-ui`, `expo:expo-ui`, `expo:expo-animation`,
     `expo:expo-design-system`, `expo:expo-router`;
   - `feature-builder-mobile-data`: `expo:expo-data-fetching`;
   - `feature-builder-mobile-fullstack`: suma obu list.

   Usunąć `expo-tailwind-setup`. Nie preładowywać `expo:expo-overview` (R7).
5. Hook `mobile-anti-pattern-check.sh` i `dev-plan` §166: tabela RN-vs-web i reguła `@expo/ui` muszą gdzieś żyć. W tej
   opcji trzeba je przenieść do reguł (`rules/`), bo nie będzie lokalnego huba.
6. Bramka „plugin włączony” w doctorze/bootstrapie (R2).
7. Etap 5 planu: świeżość zapewnia upstream, a skrypt odświeżania kopii jest niepotrzebny.

### Opcja B: kopia

1. Skrypt `stacks/expo/odswiez-expo-skills.sh`:
   - klon płytki `expo/skills`, podmiana `plugins/expo/skills/<skill>` 1:1;
   - zachowanie polskiego `description`, wycięcie „Submitting Feedback” i `agents/`;
   - raport różnic, wpis SHA w `ZRODLA-SZABLONU.md`.
2. Natychmiastowy sync do `a9e5bd3` (poprawki z §2.3).
3. Decyzja per nowy skill (`eas-update`, `expo-examples`…), bo każdy dodany to kolejna kopia do utrzymania.
4. Lokalny hub: przemianować albo świadomie przesłonić upstreamowy `expo-overview` (dziś przesłania niejawnie).
5. `expo-tailwind-setup`: zamrożony na `472d040` albo przejęty jako nasz skill.

### Opcja C: hybryda (rekomendowana)

1. Wszystko z opcji A, punkty 1–4, 6 i 7.
2. **Lokalny hub stosu** pod nową nazwą (np. `expo-stos-szablonu`; bez kolizji z `expo:expo-overview`). Treść:
   - tabela RN vs web;
   - reguła `@expo/ui` (pułapki `List`/`BottomSheet`);
   - Supabase jako domyślny backend (`eas-hosting` tylko z wyboru);
   - E2E wyłącznie Maestro (R8);
   - zakaz wysyłki feedbacku do Expo (R1);
   - skrót upstreamowych „Shared setup rules” (wykrycie SDK, dokumentacja pinowana do wersji, `npx expo install`);
   - odesłania do skilli `expo:*`.

   Preładowany w trzech builderach zamiast `expo-overview`. Hook i `dev-plan` §166 kierują na nową nazwę.
3. **`expo-tailwind-setup` jako skill lokalny** (nasza własność), objęty audytem świeżości razem z A0.3. Do rozważenia
   zmiana nazwy na `nativewind-setup`, żeby nie sugerowała, że to skill upstreamu.
4. Zmiany w treści skilli lokalnych:
   - `ux-ui-guidelines-mobile` i `security`: odwołania do skilli Expo z przedrostkiem `expo:`;
   - `expo-module`: lokalne zdanie znika razem z kopią;
   - README: sekcja „Skille `expo-*` / `eas-*` (upstream-owned)” przepisana na „plugin `expo`”.
5. Nowe skille: żadnego nie preładowywać. `eas-update`, `expo-examples` i `eas-observe` są dostępne przez narzędzie
   Skill na żądanie. W hubie warto wskazać `expo:expo-examples` przy integracjach (Supabase, Stripe) i `expo:eas-update`
   przy OTA. Tester E2E bez zmian (`mobile-e2e-maestro`).
6. Ścieżka migracji projektów potomnych (`gramywpadla`, `Nawykometr`): sync-template musi **usunąć** stare katalogi
   `expo-*`. Inaczej kolizja z §6.2 sprawi, że nazwy bez przedrostka trafią w starą kopię. Agenci z przedrostkiem są na
   to odporni.

## 9. Otwarte pytania

1. **NativeWind:** czy zespół NativeWind publikuje oficjalny skill albo plugin dla agentów, na który upstream Expo
   przerzucił odpowiedzialność (`a8f0b6c`)? Jeśli tak, czy brać go zamiast własnego `expo-tailwind-setup`? Czy stos
   szablonu zostaje przy NativeWind v5 (preview)?
2. **Przypięcie wersji pluginu:** czy marketplace Claude Code pozwala przypiąć `expo@expo-plugins` do SHA? Plugin leży
   w podkatalogu `plugins/expo`, więc chodziłoby o źródło typu `git-subdir` z `ref`/`sha` we własnym marketplace.
   Czy auto-aktualizacja marketplace'ów spoza Anthropic jest domyślnie wyłączona? Od tego zależy, czy R3 to realne
   ryzyko między runami.
3. **Skuteczność `permissions.deny` w trybie autopilota:** czy reguła `deny` na `agent-cli` blokuje Bash także w trybie
   bez pytań o zgodę, w którym działają buildery? Wymaga próby (np. `claude -p` z
   `--permission-mode bypassPermissions` i `--settings` z regułą `deny`).
4. **MCP `expo`:** zostawić (narzędzia `observe_*` dla `eas-observe` po zalogowaniu operatora) czy wyłączyć? Jak wyłączyć
   serwer MCP pluginu na poziomie projektu, nie wyłączając pluginu?
5. **Nazwa lokalnego huba** (`expo-stos-szablonu`, `mobile-stack`, …) i czy jego treść częściowo nie należy raczej do
   `rules/` (reguła `@expo/ui`, RN vs web), skoro hook się na nią powołuje.
6. **Czy agenci mają dostawać `expo:expo-overview`?** Rekomendacja: nie (R7). Trzeba to potwierdzić przy przeglądzie
   promptów builderów (A0.1 grupa C/E).
7. **Liczba „16”** w README i hubie jest nieścisła (17 katalogów). Problem znika przy przejściu na plugin, ale trzeba
   go poprawić, jeśli zostaje kopia.
