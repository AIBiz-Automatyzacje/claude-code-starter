- Kolejność: statyczny token (jeśli skonfigurowany, `timingSafeEqual` jak dziś) → lookup `sha256(bearer)` w `mcp_tokens` **przy każdym żądaniu** → mint/cached sesja → `authInfo.token` = access token usera (`clientId: 'mcp-db-token'`). Na tej ścieżce `x-supabase-access-token` ignorowany. Decyzje 1–3.
- Jednolite 401 (`UNAUTHORIZED_BODY`) dla: braku tokenu, złego statycznego, nietrafionego hasha, tokenu unieważnionego.
- Sekrety nigdy w logach (dyscyplina z fazy 2, `redactSecretFields` w shared); błędy mintowania sesji do Sentry, klientowi wyłącznie 401/500 bez treści.
- Testy jednostkowe z mockiem klienta Supabase (mockujemy zewnętrzny serwis, nie testowaną logikę).

**Notatka wykonawcza:** middleware auth to kod bezpieczeństwa — zacznij od failing testów kontraktu (401 dla każdej złej ścieżki, ścieżka legacy nienaruszona), dopiero potem implementacja.

**Wzorce do naśladowania:** obecny middleware Bearer w `server.ts` (linie ~231–241), `createSupabaseOfferPublisher` (klient per wywołanie), `createAdminClient` z `scripts/seed-test-users.ts`.

**Scenariusze testowe:**
- [Unit] statyczny Bearer poprawny → ścieżka legacy: `authInfo` z `x-supabase-access-token` (kontrakt fazy 2 bez zmian).
- [Unit] token z bazy poprawny → `authInfo.token` = zmintowany access token; `x-supabase-access-token` z cudzym JWT jest ignorowany.
- [Unit] token nieznany / unieważniony (brak wiersza) → 401 identyczne bajt w bajt z odpowiedzią dla złego statycznego.
- [Unit] brak `MCP_BEARER_TOKEN` w konfigu → mechanizm statyczny martwy, tokeny z bazy działają (stan po kroku 2.4).
- [Unit] cache sesji: drugi request tego samego usera nie mintuje ponownie; unieważnienie tokenu odcina dostęp mimo żywej sesji w cache'u (lookup per żądanie).

**Weryfikacja:**
- `pnpm typecheck`, `pnpm test`, `pnpm build` przechodzą.
